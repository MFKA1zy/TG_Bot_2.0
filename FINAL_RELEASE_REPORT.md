## Обнаруженные проблемы и исправления

1. Обычный запуск всегда читал `.env`, безопасного отдельного launcher не было.
   Добавлены `ENV_FILE`, `.env.test.example` и `tools/run_staging.py` с очисткой
   унаследованных настроек/секретов, проверкой известных production-путей и
   токена. `--check` не запускает сеть и не создаёт тестовую базу.
2. Маскировался лишь BOT_TOKEN в одном обработчике ошибок; traceback и логи
   библиотек могли вывести ImgBB key, activation code или proxy credentials.
   Общий formatter маскирует секреты после форматирования, включая исключения
   и Telegram bot URL. Добавлена ротация log-файла: 5 MiB + 3 архивные копии.
3. Закрытие Telegram-сессии не ожидало незавершённые update/background tasks.
   Shutdown отменяет рассылку, ждёт задачи до 15 секунд, затем отменяет и
   дожидается rollback, маркирует незавершённые рассылки interrupted, закрывает
   storage и сессию. Для Railway рекомендован draining 30 секунд. Используется
   private task registry **зафиксированного aiogram 3.15.0**: при обновлении
   зависимости повторить проверку shutdown. SQL-соединения scoped и закрываются.
4. aiogram MemoryStorage сохранял пустую запись даже при чтении/очистке формы
   каждого посетителя. Совместимый `PruningMemoryStorage` не создаёт записи
   на чтении и удаляет пустые после clear. Проверено на 2000 пользователях.
   Незавершённые формы остаются в RAM и сбрасываются при рестарте, как раньше;
   бизнес-операции и антинакрутка хранятся в SQLite. Длительный live soak памяти
   не проводился; TTL для брошенных форм в эту фазу не добавлялся.
5. Не было проверяемой процедуры preflight всего набора данных перед выпуском.
   Новые `snapshot_data.py` и `migration_preflight.py` используют SQLite backup
   API, проверяют целостность/количества/старые строки и JSON. Миграции запускаются
   только на выходной копии, дважды; проверки не отключаются `python -O`.

Новых миграций схемы фаза 6 не добавляет. Сохраняются миграции 3/4/5, SQLite WAL,
DATA_DIR, единый баланс, ID сериалов и прежние механизмы защиты/кэширования.

Процесс в тесте реально завершался через `os._exit(7)` после ledger UPDATE/INSERT

shutdown. Ошибки отправки Telegram и SQLite busy/locked покрыты прежними и
новыми проверками; реальные токены/реальные пользователи в тестах не участвовали.

`tools/check_release.py`: компиляция, diff check, шаблоны секретов и совпадение

## Переменные и эксплуатационные ограничения

Новая **необязательная** переменная приложения `ENV_FILE` выбирает отдельный
dotenv-файл; если явно заданный файл отсутствует, запуск завершается ошибкой,
без fallback к production `.env`. Для Railway обычный путь — Variables,
`ENV_FILE` не задавать. Остальные переменные и зависимости сохранены.
Для staging использовать отдельные токен, канал, DATA_DIR/SQLite и Volume.
`RAILWAY_DEPLOYMENT_DRAINING_SECONDS=30` — рекомендуемая настройка платформы.

В репозитории нет подключённого доступа к Dashboard/CLI Railway: реальный
serverless/sleep, restart policy, Variables и mount не подтверждены. Не создан
новый конфиг, который мог бы изменить production. Фактические параметры
владелец сверяет по [RAILWAY_DEPLOY_GUIDE.md](RAILWAY_DEPLOY_GUIDE.md).

## Backup, миграция и откат

Сначала остановить все писатели, получить SQLite backup API + согласованные
JSON, сохранить manifest и внешний архив; отдельно Railway Volume backup.
Затем preflight экспортированной копии и два повторных startup migration.
После живой проверки staging и отдельного одобрения — production deployment.
При ошибке сохранить post-failure snapshot. Откат образа не отменяет схему;
старую базу не восстанавливать поверх новых пользователей и транзакций.
Подробности: [RAILWAY_DEPLOY_GUIDE.md](RAILWAY_DEPLOY_GUIDE.md),
[ROLLBACK_PLAN.md](ROLLBACK_PLAN.md).

1. Создать тестового бота/канал, вручную заполнить `.env.test`, включить inline.
2. Пройти live-матрицу [STAGING_TEST_PLAN.md](STAGING_TEST_PLAN.md) на телефоне;

3. Зафиксировать фактическую старую production-версию и пути данных; проверить
   Variables, один polling, Python 3.12, Volume, sleep/restart/draining.
4. В согласованное окно сделать и проверить полный backup, вынести архив.
5. Запустить preflight фактического экспорта; сравнить пользователей, флаги,
   роли, каталог, ID, постеры, ссылки, настройки и integrity/FK.
6. Одобрить конкретный release commit; лишь затем выполнить deployment.
7. Проверить логи, smoke и сохранность после рестарта; держать оба snapshot
   для контролируемого rollback без потери новых записей.
