# Фаза 4 — профили, баллы и таблица лидеров

Дата: 2026-10-24. Основа `c11e9c9`, ветка
`feature/profiles-points-leaderboard`. Production Railway не изменялся.

## Реализовано

- «Мой профиль»: имя/username, дата регистрации, баланс, всего заработано и
  списано, количество просмотров/оценок/опубликованных отзывов/избранного, место
  в рейтинге. Отдельные страницы просмотренных, избранного, своих оценок,
  отзывов и журнала баллов с пагинацией. Используются существующие users,
  confirmed_views, favorites, ratings и reviews, без второго хранилища аккаунтов.
- Первый новый подтверждённый просмотр приносит 10 баллов по умолчанию.
  Награда изменяется администрацией (0–1000000). Просмотр, ledger и изменение
  итогов пользователя фиксируются одной BEGIN IMMEDIATE транзакцией.
- Повторный callback, двойное нажатие, параллельные запросы и рестарт не дают
  повторной награды. Открытие карточки, просмотр меню подтверждения и TikTok
  не начисляют баллы. Подтверждение остаётся самостоятельным действием пользователя.
- Журнал содержит ID, пользователя, тип, signed amount, причину, серию/снимок
  названия, UTC, администратора, уникальный ключ и баланс после операции.
  Удаление серии из JSON не удаляет журнал. Ограничение UNIQUE(user,series)
  для view защищает от повторной награды даже с другим ключом операции.
- Баланс, заработано и списано хранятся в users. Все положительные операции,
  включая ручные начисления, увеличивают earned; отрицательные увеличивают
  spent. Списание не уменьшает достижения earned. Баланс не может стать
  отрицательным. Балансы не кэшируются.
- Таблица лидеров: по 10 пользователей, собственное место, страницы, имена
  без публичного Telegram ID. По умолчанию earned, переключение на balance
  доступно в админке. Ban исключает пользователя; равенства разрешаются по
  telegram_id по возрастанию. SQL использует индексы и LIMIT/OFFSET;
  все пользователи не загружаются в Python для сортировки.
- /admin → «Экономика»: статистика, поиск пользователя, баланс, журнал с
  администратором операции, ручное начисление/списание, награда, критерий
  рейтинга, лидеры, аудит расхождений и предварительный расчёт старых наград.
- Ручная операция: пользователь → положительная сумма → причина → preview →
  подтверждение. До последнего шага баланс не меняется. Подтверждение связано
  с FSM и конкретным сообщением. Роль и ban администратора повторно проверяются
  в транзакции. Административные изменения — явные действия уполномоченного
  оператора; активность пользователя дополнительно требует капчу/подписку.
- Аудит ищет расхождения balance/earned/spent с журналом и 100+ операций
  за текущий UTC-день. Это сигнал для ручной проверки, без автоматических санкций.
- Все новые сообщения/кнопки RU/UK/EN. Общий authorize и ban middleware
  сохранены: профиль и пользовательские награды защищены капчей, живой
  подпиской и ban; внутри начисления повторно проверяются пользователь/капча/ban.

## Политика старых просмотров

При миграции существующие confirmed_views получают reward_eligible=0.
Новые подтверждения вставляются с reward_eligible=1. Это колонка прежней
таблицы, а не второй механизм просмотров. Инициализация **не начисляет** баллы.
Повторное нажатие для старого просмотра также не даёт награды.

Административная процедура:

1. /admin → Экономика → Расчёт наград за старые просмотры.
2. Без изменения данных выводятся пользователи, просмотры, награда и сумма.
   Учитываются записи с существующим незаблокированным пользователем без
   операции view в ledger. Исторические ID, включая удалённые серии, сохраняются.
3. Сохраняется только FSM-preview с SHA-256 fingerprint списка, времён
   подтверждений и суммы награды. До подтверждения нет записей наград/баллов.
4. При подтверждении сервер повторяет расчёт внутри транзакции. Изменённый
   набор или награда делают preview устаревшим; потребуется новый расчёт.
5. Начисления и audit-запись фиксируются вместе. Повторное применение одного
   preview ничего не начисляет. Повторный расчёт исключает уже награждённые пары.
   Ошибка любой операции откатывает весь batch.

Исторические записи без существующего пользователя не удаляются и не
награждаются. Заблокированные исключены из расчёта. Награда 0 также создаёт
идемпотентную запись, поэтому изменение настройки позже не даёт второй награды.
Для большого production-набора процедуру следует сначала проверить на копии:
применение идёт одной транзакцией, другие записи SQLite в это время ожидают.
Процедура не запускалась на реальных данных в этой работе.

## SQLite и безопасность

Миграция version=4 добавляет:

- users.points_balance / points_earned / points_spent: INTEGER, DEFAULT 0,
  CHECK 0..9000000000000000;
- confirmed_views.reward_eligible: DEFAULT 0;
- points_ledger с FK пользователей/администраторов и уникальными ключами;
- economy_settings и economy_audit;
- индексы ledger по user/id и дате, partial UNIQUE view, два индекса
  лидерборда, индекс исторических просмотров и user/status отзывов.

Перед первым изменением существующей базы создаётся SQLite backup рядом
с ней. ALTER выполняется только для отсутствующих колонок, таблицы/индексы
создаются идемпотентно. Текущие пользователи, просмотры, рейтинг и отзывы
не удаляются. Повторная инициализация не обнуляет баланс и не изменяет
классификацию уже записанных просмотров. Экономика использует прежние
асинхронные connection helpers с foreign_keys=ON, параметрами и rollback.

Сумма ручной операции: 1..1000000000; списание ограничено доступным балансом.
Текущий баланс берётся из SQLite в транзакции, не из callback/FSM. Пользователь
в профиле определяется только из from_user; callback не может выбрать чужой
аккаунт. Просмотры проверяют опубликованность в существующем CatalogService.

## Railway и файлы

Сохраняются `python main.py`, polling, Python 3.12, aiogram 3, DATA_DIR=/data,
DB_PATH, RU/UK/EN, inline-поиск и кэш фазы 3. Все данные экономики находятся
в прежней SQLite. Перед выкладкой остановить прежний polling, сохранить
внешний SQLite backup и DATA_DIR, проверить version=4 на копии, integrity_check,
foreign_key_check, пользователей, старые просмотры, нулевые начальные балансы,
новое начисление и повторное нажатие. Смена DATA_DIR требует предварительного
переноса фактической рабочей базы. Backup рядом с базой не заменяет внешнюю копию.

Новые файлы: database/economy_schema.py, database/economy_repository.py,
handlers/profile.py, handlers/admin/economy.py, tools/benchmark_points.py,
tests/test_points_phase4.py, tests/test_points_handlers.py,
benchmarks/phase4-points.json и этот отчёт.

Обновлены: database/connection.py, database/catalog_repository.py,
services/catalog_service.py, handlers/catalog.py, регистрация routers в main.py
и handlers/admin/__init__.py, обе клавиатуры меню, RU/UK/EN, связанные тесты,
README.md и DEVELOPMENT_PROGRESS.md.
