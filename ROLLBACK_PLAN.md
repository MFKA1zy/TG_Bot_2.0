# План отката

Production-действия выполняет владелец после оценки состояния. Автоматического
восстановления старой базы и автоматической обратной миграции нет.

1. Остановить новый polling и все писатели. Не запускать старый и новый образы
   одновременно с одним токеном. Зафиксировать ошибку, deployment ID и время.
2. Сохранить **текущее** состояние после неудачного обновления: отдельный
   SQLite backup API снимок, JSON, manifest и логи. Не затирать этот снимок
   исходным pre-release backup. Он может содержать новые регистрации, отзывы,
   подтверждения, награды и изменения администраторов.
3. Определить, применились ли миграции и появились ли новые записи. Откат
   образа Railway сам по себе не возвращает SQLite/JSON к прежней версии.
4. Если ошибка только в коде, предпочтителен исправленный совместимый commit.
   Старый образ можно вернуть с текущими данными **лишь после** теста на копии:
   старый код может перезаписать неизвестные JSON-поля, повторно использовать
   ID или не понимать расширенные типы ledger. Обратная совместимость
   произвольной старой production-версии не подтверждена.
5. Если новых записей после backup точно нет и восстановление одобрено,
   восстановить согласованную пару SQLite+JSON из проверенного pre-release
   backup в отдельную подготовленную директорию/том. Проверить SHA-256,
   integrity/FK, количества/ID/постеры/TikTok и настройки. Подключение
   восстановленного тома выполняется только при остановленных процессах.
   Не оставлять WAL/SHM от другой базы рядом с восстановленным файлом.
6. Если новые записи **есть**, не подменять текущую базу старой автоматически.
   Сохранить обе версии; либо исправить текущую схему вперёд, либо подготовить
   отдельный проверяемый перенос новых строк и балансов. Сверить ledger,
   spins и confirmed_views по уникальным ключам, пользователей по telegram_id,
   связи и монотонные ID. Ручное сведение баланса без журнала недопустимо.
   Решение о возможной потере данных требует отдельного решения владельца.
7. До повторного открытия проверить восстановленный образ на копии данных,
   единственный polling, путь Volume, капчу/подписку/ban, старый аккаунт,
   каталог, inline и отсутствие повторных начислений. Отменённые рассылки
   автоматически не возобновлять: неизвестен точный факт доставки в момент сбоя.
8. Записать итог, сохранённые архивы, commit и результаты smoke. Сохранить
   post-failure snapshot до завершения разбора.

Railway Volume backup восстанавливается платформой только в том же
project/environment; восстановление вызывает redeploy. Перед этим также
сохранить текущие данные. См. [официальную документацию backup](https://docs.railway.com/volumes/backups).
